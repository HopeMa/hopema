# MySQL · Redis · Kafka 与高并发高可用系统设计
## 后端存储与架构知识体系 · 由浅入深

> **一句话定位**：MySQL 负责**可靠存储**（事务、强一致），Redis 负责**高速读写**（缓存、数据结构），Kafka 负责**异步解耦与削峰**（消息流）。三者组合 + 无状态应用层 = 高并发高可用系统的基石。

### 📚 知识体系总览

1. **MySQL**：InnoDB、B+ 树索引、事务/MVCC、锁、三大日志、SQL 优化、主从复制、分库分表
2. **Redis**：数据结构、持久化、过期淘汰、缓存三大问题、一致性、分布式锁、哨兵与集群、大 key 热 key
3. **Kafka**：架构与分区、高性能原理、生产/消费可靠性、Rebalance、积压处理、MQ 选型
4. **高并发设计**：缓存/异步/拆分方法论、限流算法、熔断降级、负载均衡、多级缓存、秒杀实战
5. **高可用设计**：SLA 度量、冗余切换、各组件 HA 矩阵、降级预案、异地多活、混沌工程
6. **综合场景**：缓存+DB 架构、分布式事务、系统演进路线、线上问题排查

## 第一部分：MySQL（关系型数据库）

### Q1：InnoDB 和 MyISAM 的区别？为什么默认 InnoDB？

**答：**

| 维度 | InnoDB | MyISAM |
| --- | --- | --- |
| 事务 | ✅ 支持 ACID | ❌ 不支持 |
| 锁粒度 | 行级锁（+ 表锁） | 只有表锁 |
| 外键 | ✅ 支持 | ❌ |
| 崩溃恢复 | ✅ redo log 保证 | ❌ 崩溃易损坏 |
| MVCC | ✅ 支持 | ❌ |
| 聚簇索引 | ✅（索引即数据） | ❌（索引与数据分离） |
| 适用 | 绝大多数 OLTP 场景 | 读密集、可容忍丢数据的场景（已被淘汰） |

**面试要点**：互联网业务几乎全用 InnoDB——事务 + 行锁 + 崩溃恢复是生产刚需。

### Q2：MySQL 为什么用 B+ 树做索引？不用 B 树、哈希、红黑树？

**答：**

* **vs 哈希**：哈希等值查询 O(1) 很快，但**不支持范围查询和排序**（`WHERE age > 18` 无能为力）
* **vs 红黑树/二叉树**：二叉树太高瘦，千万数据层级深达几十层 → 每层都是一次磁盘 IO，太慢
* **vs B 树**：B 树每个节点都存数据，单页（16KB）能放的键少 → 树更高；B+ 树**非叶子节点只存键**，扇出更大
* **B+ 树优势**：
  1. 矮胖：3~4 层即可支撑**千万级数据**（根节点常驻内存，一次查询仅 1~3 次磁盘 IO）
  2. 叶子节点用**双向链表**连接：范围查询、排序扫库极快
  3. 所有查询都要走到叶子节点，**性能稳定**

### Q3：聚簇索引、二级索引、回表、覆盖索引、索引下推分别是什么？

**答：**

* **聚簇索引（主键索引）**：叶子节点存**整行数据**——"索引即数据，数据即索引"
* **二级索引（辅助索引）**：叶子节点存**索引列 + 主键值**（不是行地址）
* **回表**：走二级索引查到主键后，**再回聚簇索引查整行**——多一次树查找
  * 例：`SELECT * FROM user WHERE name = '张三'`（name 有索引）→ 先查 name 索引树拿 id，再回主键树取整行
* **覆盖索引**：查询所需字段**全部包含在索引里**，无需回表
  * 例：`SELECT id, name FROM user WHERE name = '张三'` → name 索引树直接返回
  * 优化技巧：把高频查询的 select 字段做成联合索引，`Extra: Using index` 即命中
* **索引下推（ICP，5.6+）**：在存储引擎层先用索引中已有的列过滤，减少回表次数
  * 例：索引 `(name, age)`，查询 `WHERE name LIKE '张%' AND age = 20` → 引擎层先用 age 过滤，回表量骤减

### Q4：最左前缀原则是什么？哪些情况索引会失效？

**答：**

**最左前缀原则**：联合索引 `(a, b, c)` 相当于建了 `(a)`、`(a,b)`、`(a,b,c)` 三个索引——查询条件必须从最左列开始连续命中。

```
索引 (a, b, c)
✅ WHERE a=1 AND b=2 AND c=3     全命中
✅ WHERE a=1 AND b=2             命中 a,b
✅ WHERE b=2 AND a=1             命中 a,b（优化器会调整顺序）
❌ WHERE b=2 AND c=3             不命中（缺了 a）
✅ WHERE a=1 AND c=3             只命中 a（c 用不上索引，但可 ICP）
⚠️ WHERE a>1 AND b=2             a 范围后 b 失效（范围之后全失效）
```

**常见索引失效场景**：

1. 对索引列做**函数或运算**：`WHERE YEAR(create_time)=2024`
2. **隐式类型转换**：字符串列用数字查 `WHERE phone = 13800000000`
3. **左模糊**：`LIKE '%abc'`（`'abc%'` 可以走）
4. `OR` 连接了非索引列
5. `!=`、`NOT IN`、`IS NOT NULL`（区分度低时优化器放弃）
6. 优化器评估**回表代价过高**（区分度低、命中行太多）宁愿全表扫

### Q5：索引设计有哪些规范？

**答：**

1. 主键用**自增或有序 ID**（避免 UUID 随机写导致页分裂）
2. 联合索引把**区分度高的列放左边**（`count(distinct col)/count(*)` 越接近 1 越好）
3. 覆盖高频查询：让 `SELECT` 的字段尽量落在索引中
4. **控制索引数量**：单表建议 ≤ 5 个——每个索引都拖慢写入、占空间
5. 长字符串用**前缀索引**（`INDEX(email(10))`）或哈希列
6. 不给低区分度列单独建索引（性别、状态）
7. 外键列、JOIN 列、ORDER BY / GROUP BY 列考虑索引

### Q6：ACID 分别靠什么实现？

**答：**

| 特性 | 含义 | 实现手段 |
| --- | --- | --- |
| **A** 原子性 | 全成功或全回滚 | **undo log**（逻辑回滚日志） |
| **D** 持久性 | 提交即落盘不丢 | **redo log**（WAL 先写日志） |
| **I** 隔离性 | 事务互不干扰 | **锁 + MVCC** |
| **C** 一致性 | 数据合法状态 | A + I + D + 约束共同保证 |

**WAL（Write-Ahead Logging）**：先写日志再写数据页——顺序写日志远快于随机写数据页，这是 InnoDB 高吞吐的关键。

---

### Q7：四种隔离级别与并发读异常？

**答：**

| 隔离级别 | 脏读 | 不可重复读 | 幻读 | 实现 |
| --- | --- | --- | --- | --- |
| 读未提交 RU | ❌ 可能 | ❌ 可能 | ❌ 可能 | 直接读最新版本 |
| 读已提交 RC | ✅ 避免 | ❌ 可能 | ❌ 可能 | MVCC：每条语句生成 ReadView |
| **可重复读 RR（默认）** | ✅ 避免 | ✅ 避免 | ⚠️ 基本避免 | MVCC：事务首查生成 ReadView + 临键锁 |
| 串行化 | ✅ 避免 | ✅ 避免 | ✅ 避免 | 全表加锁，读加共享锁 |

* **脏读**：读到别人未提交的数据
* **不可重复读**：同一事务两次读同一行值不同（别人 UPDATE 了）
* **幻读**：同一事务两次范围查询行数不同（别人 INSERT 了）

**面试要点**：InnoDB 的 RR 通过 **MVCC 解决快照读幻读**，通过 **Next-Key Lock（临键锁）解决当前读幻读**。

### Q8：MVCC 的实现原理？

**答：** Multi-Version Concurrency Control——**读不加锁，读写不冲突**。三要素：

1. **隐藏列**：每行有 `trx_id`（最近修改事务 ID）和 `roll_pointer`（指向 undo log 版本链）
2. **undo log 版本链**：旧版本通过 roll_pointer 串成链表
3. **ReadView（一致性视图）**：记录生成视图时"活跃（未提交）事务集合"

**可见性判断**：沿版本链从新到旧找第一个满足以下条件的版本——

* 该版本的 trx_id 不是当前事务自己
* 该版本的 trx_id 不在活跃集合中（已提交）
* trx_id 小于活跃集合最小值（在视图创建前已提交）

**RC 与 RR 的区别只有一处**：RC **每条语句**生成新 ReadView（所以能看到别人最新提交）；RR **只在事务第一次查询**时生成并复用（所以可重复读）。

### Q9：InnoDB 的锁体系？死锁怎么排查与避免？

**答：**

**锁粒度层级**：

* 全局锁（FTWRL，全库逻辑备份）
* 表级锁（表锁、MDL 元数据锁、意向锁、AUTO-INC 锁）
* 行级锁（基于索引实现）：
  * **Record Lock 记录锁**：锁单条索引记录
  * **Gap Lock 间隙锁**：锁索引记录之间的间隙（RR 级别防幻读插入了，唯一索引等值命中可退化为记录锁）
  * **Next-Key Lock 临键锁**：记录锁 + 间隙锁，左开右闭区间 `(a, b]`

**关键规则**：**行锁加在索引上**——条件列没索引会升级为全表扫描，所有行的间隙都被锁 ≈ 锁表！

**死锁排查**：`SHOW ENGINE INNODB STATUS` 的 LATEST DETECTED DEADLOCK 段；开启 `innodb_print_all_deadlocks` 记录所有死锁日志。

**避免死锁**：

1. 多表/多行操作**按相同顺序**访问
2. 小事务，尽快提交，缩短锁持有时间
3. 给条件列建索引，避免锁范围扩大
4. 降低隔离级别（RC 没有间隙锁）
5. 必要时显式锁定：`SELECT ... FOR UPDATE`

### Q10：redo log、undo log、binlog 各是什么？两阶段提交为什么必要？

**答：**

| 日志 | 层级 | 性质 | 作用 |
| --- | --- | --- | --- |
| **redo log** | InnoDB 引擎层 | 物理日志（页修改） | 崩溃恢复，保证持久性；循环写 |
| **undo log** | InnoDB 引擎层 | 逻辑日志（反向操作） | 回滚 + MVCC 版本链 |
| **binlog** | Server 层 | 逻辑日志（SQL/行变更） | **主从复制、数据归档恢复**；追加写 |

**binlog 三种格式**：STATEMENT（记 SQL，可能主从不一致）、**ROW（记行变更，默认，最安全）**、MIXED。

**两阶段提交（2PC）保证 redo 与 binlog 一致**：

```
1. redo log 写入，状态 = prepare
2. 写 binlog
3. redo log 状态 = commit
崩溃恢复规则：
  - redo 已 commit → 提交
  - redo prepare → 看 binlog 是否完整：完整则提交，不完整则回滚
```

如果没有 2PC：先写 redo 后写 binlog 崩溃 → 主库有数据从库没有；反之亦然——**主从数据永久不一致**。

### Q11：如何做 SQL 优化？EXPLAIN 重点看什么？

**答：**

**定位慢 SQL**：慢查询日志（`long_query_time`）、DRDS/监控平台、`performance_schema`。

**EXPLAIN 关键字段**：

| 字段 | 关注点 |
| --- | --- |
| **type** | 访问类型，好坏排序：`system > const > eq_ref > ref > range > index > ALL`；出现 ALL（全表扫）通常要优化 |
| **key / key_len** | 实际用的索引及长度（判断联合索引用了几列） |
| **rows** | 预估扫描行数 |
| **Extra** | `Using index`（覆盖索引✅）、`Using filesort`（额外排序❌）、`Using temporary`（临时表❌）、`Using index condition`（ICP） |

**优化清单**：只查需要的列；建合适索引消除 ALL/filesort；小表驱动大表 JOIN；`JOIN` 字段类型一致且建索引；深分页优化（见 Q12）；必要时用 `FORCE INDEX` 纠正优化器。

### Q12：深分页 `LIMIT 1000000, 10` 为什么慢？怎么优化？

**答：** MySQL 会取出前 1000010 行再丢弃前 100 万行——扫描和回表开销巨大。

**优化方案**：

```sql
-- 1. 游标/书签法（连续翻页场景，最优）
SELECT * FROM t WHERE id > 1000000 ORDER BY id LIMIT 10;

-- 2. 延迟关联：先用覆盖索引拿到 id，再回表 10 行
SELECT t.* FROM t
JOIN (SELECT id FROM t ORDER BY create_time LIMIT 1000000, 10) tmp
ON t.id = tmp.id;
```

**大表 count 优化**：`COUNT(*)` 全表扫描很慢 → 维护计数表（触发器/业务更新）、Redis 计数缓存、或允许近似值 `EXPLAIN` 估算。

### Q13：主从复制的原理？主从延迟怎么处理？

**答：**

**复制流程（异步默认）**：

```
主库事务提交 → 写 binlog
从库 IO 线程 → 拉取 binlog → 写入 relay log（中继日志）
从库 SQL 线程 → 重放 relay log
```

**三种复制方式**：异步（默认，可能丢）、**半同步**（至少 1 个从库 ACK 才返回，折中）、**GTID 复制**（事务全局唯一标识，搭从库/故障切换更方便）。

**主从延迟成因**：大事务、从库单线程重放（可开并行复制 `slave_parallel_workers`）、从库机器差、读压力大。

**应对策略**：

1. **写后读强制走主库**（关键业务）
2. 二次查询：写完后短暂 sleep/版本号校验再读从库
3. 半同步 + 并行复制降低延迟
4. 大事务拆小，避免 `DELETE 100 万行`（分批删）

### Q14：什么时候分库分表？怎么分？

**答：**

**触发信号**：单表数据量过大（经验值 **2000 万行或 20GB** 以上 B+ 树变高、维护成本升）、单库写入 QPS 到瓶颈、磁盘 IO 打满。

**拆分方式**：

* **垂直分库**：按业务域拆（订单库/用户库/商品库）——微服务配套
* **垂直分表**：冷热列分离（大字段拆出去）
* **水平分库分表**：同构表按分片键散到多库多表——解决容量与写入瓶颈

**分片键选择**：高频查询维度（如 `user_id`），让核心查询尽量路由到单库。

**分片算法**：hash 取模（均匀，扩容难）、**范围**（好扩容，易热点）、**一致性哈希**（折中）；基因法解决多维查询。

**分库分表带来的新问题**：

1. 跨库 JOIN → 业务聚合 / 冗余字段 / ES 宽表
2. 跨库事务 → 分布式事务（见第六部分）
3. **分布式 ID** → 雪花算法（Snowflake）、号段模式、UUID 不适合做主键
4. 二次分页/排序/聚合 → 各分片归并（中间件做）或走 ES/数仓
5. 扩容数据迁移 → 双写方案、一致性校验

**中间件**：ShardingSphere（主流）、MyCat。

### Q15：MySQL 高可用有哪些方案？

**答：**

| 方案 | 原理 | 特点 |
| --- | --- | --- |
| **主从 + MHA/Orchestrator** | 监控主库，故障时提升从库 | 经典方案，切换有秒级中断 |
| **半同步复制** | 至少一个从库收到 binlog 才提交 | 降低丢失窗口，仍有极端丢失风险 |
| **MGR（组复制）** | Paxos 变种协议多数派提交 | 强一致、自动选主，要求高 |
| **分布式数据库** | TiDB、OceanBase 等 | 原生分布式、自动分片，运维复杂度转移 |

**配套要点**：VIP/DNS/Proxy 切换流量（ProxySQL、MySQL Router）、MHA 的 SSH 互信与 binlog 补齐、演练切换流程。

## 第二部分：Redis（缓存与分布式数据结构）

### Q16：Redis 为什么这么快？

**答：**

1. **纯内存**操作（对比 MySQL 磁盘 IO）
2. **单线程命令处理**（6.0 前）：无锁竞争、无上下文切换（IO 多路复用 epoll）
3. **高效数据结构**：SDS、跳表、压缩列表、渐进式 rehash 的字典
4. 6.0 引入**多线程 IO**（只并行读写 socket 与协议解析，命令执行仍单线程）

**面试要点**：单线程为什么还快？——瓶颈不在 CPU 而在内存和网络，单线程反而避免了锁开销；也因此**大 key 会阻塞所有请求**（见 Q29）。

### Q17：五大数据类型的应用场景与底层结构？

**答：**

| 类型 | 底层结构 | 典型场景 |
| --- | --- | --- |
| **String** | SDS（简单动态字符串） | 缓存对象 JSON、计数器 INCR、分布式锁 |
| **Hash** | listpack / hashtable | 对象存储（可单字段更新）、购物车 |
| **List** | quicklist（双向链表+listpack） | 消息队列、最新列表 LPUSH + LRANGE |
| **Set** | intset / hashtable | 去重、标签、抽奖、共同关注（SINTER 交集） |
| **ZSet** | listpack / **跳表 + 字典** | 排行榜、延迟队列（score 为执行时间）、范围检索 |

**特殊结构**：BitMap（签到、活跃统计）、HyperLogLog（亿级 UV 估算，0.81% 误差，仅 12KB）、GEO（附近的人）、Stream（持久化消息队列）。

**加分点**：ZSet 为什么用跳表不用红黑树——实现简单、范围遍历更自然、且可按 rank 快速定位。

### Q18：RDB 和 AOF 怎么选？混合持久化是什么？

**答：**

| 维度 | RDB 快照 | AOF 日志 |
| --- | --- | --- |
| 内容 | 某时刻全量内存快照（二进制） | 每条写命令追加（文本协议） |
| 触发 | save 阻塞 / **bgsave fork 子进程** | 每次写入命令 |
| fsync 策略 | — | `appendfsync always / everysec（默认，最多丢1秒）/ no` |
| 恢复速度 | 快（直接载入） | 慢（重放全部命令） |
| 数据安全 | 可能丢最后一次快照后的数据 | 丢秒级/零丢失 |
| 文件大小 | 小、适合备份 | 大（靠 **AOF 重写** 压缩成最小命令集） |

**bgsave 原理**：fork 子进程 + **写时复制（COW）**——子进程遍历内存写快照，主进程继续服务，修改的页才会复制。

**混合持久化（4.0+，推荐）**：AOF 重写时，前半段写 RDB 全量、后半段追加增量命令——**恢复快 + 丢数据少**，兼顾两者。

### Q19：过期删除与内存淘汰策略？

**答：**

**过期删除（对到期 key）**——惰性 + 定期组合：

* **惰性删除**：访问时检查过期才删（CPU 友好，但冷 key 占内存）
* **定期删除**：每 100ms 随机抽一批带 TTL 的 key 检查，过期比例超 25% 继续抽（防阻塞）

**内存淘汰（内存达 `maxmemory` 时）**——8 种策略：

| 策略 | 范围 | 算法 |
| --- | --- | --- |
| noeviction（默认） | — | 不淘汰，写请求报错 |
| allkeys-lru | 全部 key | 近似 LRU |
| volatile-lru | 有 TTL 的 key | 近似 LRU |
| allkeys-lfu / volatile-lfu | 同上 | LFU 按频率（4.0+） |
| volatile-ttl | 有 TTL | 剩余存活时间短的先走 |
| allkeys-random / volatile-random | 同上 | 随机 |

**缓存场景推荐**：`allkeys-lru` 或 `allkeys-lfu`。

---

### Q20：缓存穿透、击穿、雪崩——三大经典问题？

**答：**

| 问题 | 定义 | 典型场景 | 解决方案 |
| --- | --- | --- | --- |
| **穿透** | 查询**根本不存在**的数据，缓存 DB 都没有，每次都打 DB | 恶意请求 id=-1 | ① 缓存空值（短 TTL）② **布隆过滤器**前置拦截 ③ 接口层参数校验/限流 |
| **击穿** | **某个热 key 过期瞬间**，海量并发同时打到 DB | 爆款商品缓存到期 | ① **互斥锁**：只放一个线程回源重建，其他等待 ② 逻辑过期（value 存过期时间，过期后异步重建） ③ 热点 key 永不过期 |
| **雪崩** | **大量 key 同时过期**或缓存**整体宕机**，DB 被冲垮 | 凌晨批量预热的 key 同时到期 | ① TTL 加**随机值**打散 ② **集群高可用**防整体宕机 ③ 多级缓存 ④ 限流降级兜底 |

**一句话区分**：穿透是"查不存在的"，击穿是"单个热 key 失效"，雪崩是"集体失效"。

### Q21：缓存与数据库一致性怎么保证？

**答：** 先明确：只要用到缓存，就只有**最终一致**，没有强一致（除非分布式锁串行化，代价极高）。

**标准方案：Cache Aside Pattern（旁路缓存）**

* 读：先读缓存 → 命中返回；未命中读 DB → 回填缓存 → 返回
* 写：**先更新 DB，再删除缓存**（不是更新缓存）

**三个高频追问**：

1. **为什么删缓存而不是更新缓存？**
   更新缓存在并发写下容易乱序覆盖（A 先写 DB 后写缓存、B 后写 DB 先写缓存→脏数据）；且缓存值可能涉及多表计算，写放大。删是幂等的懒加载。
2. **为什么先更 DB 再删缓存？**
   反过来：删缓存后、更新 DB 前另一请求读 miss → 回填**旧值** → 脏数据长期存在。
3. **先更 DB 再删缓存就万无一失？**
   极小概率：读请求 miss → 读到旧 DB 值 → 此时写请求完成更新+删缓存 → 读请求才回填旧值。概率极低（读快写慢才触发），可用**延迟双删**兜底。

**延迟双删**：更新 DB → 删缓存 → 延迟几百毫秒（等可能的回填完成）→ 再删一次。

**进阶**：订阅 **binlog（Canal）异步删缓存**——业务零侵入、不怕删失败（消息重试）；删除失败进 MQ 重试。

### Q22：Redis 分布式锁怎么实现？有哪些坑？

**答：**

**基础实现**：

```
加锁：SET lock_key unique_value NX EX 30
解锁：Lua 脚本（校验 value 是自己的才删，保证原子性）
```

**四个必答的坑**：

1. **锁误删**：A 业务超时锁自动过期 → B 拿到锁 → A 执行完把 B 的锁删了 → 加锁时存**唯一 value**，解锁用 Lua 校验再删
2. **业务超时锁过期**：看门狗续期（Redisson watchdog，默认每 10s 续到 30s）
3. **主从切换锁丢失**：主库写入锁后宕机，未同步到从库 → 新主没有锁 → B 也能加锁 → ① Redlock 红锁（多数派，有争议：时钟漂移、GC 停顿）② 强一致的锁服务（etcd/ZooKeeper/数据库锁）
4. **可重入**：同线程重复加锁不死锁 → hash 结构计数（Redisson RLock 实现）

**面试要点**：能说清"Redis 锁 = 高性能但非绝对安全；ZK/etcd 锁 = 强一致但性能低"的权衡。

### Q23：主从复制、哨兵、Cluster 的区别？

**答：**

* **主从复制**：从库 `SLAVEOF` 主库，全量同步（RDB）+ 增量同步（repl_backlog 环形缓冲区）。只解决**读扩展与数据冗余**，主挂了需**人工切换**。
* **哨兵（Sentinel）**：哨兵集群监控主从，主挂了**自动选主切换**（quorum 多数哨兵同意才判定下线）。解决**高可用**，但容量仍受单机内存限制。
* **Cluster 集群**：
  * 数据按 **16384 个 hash slot** 分片（`slot = CRC16(key) % 16384`）
  * 每个 master 负责一段 slot，Gossip 协议通信
  * 客户端直连：请求到错节点返回 **MOVED** 重定向（或 ASK 迁移中）
  * **同时解决：数据分片（容量/写扩展）+ 高可用（master 挂了 slave 顶上，无需额外哨兵）**

**限制**：多 key 操作/事务要求 key 同 slot（hash tag `{user1}...`）；不支持跨 slot 的部分命令。

### Q24：什么是大 key、热 key？怎么发现、怎么治理？

**答：**

**大 key**（value 过大或元素过多，如 String > 1MB、集合 > 1 万元素）：

* 危害：操作阻塞单线程（DEL 一个百万元素 hash）、网络打爆、主从同步慢、迁移卡顿
* 发现：`redis-cli --bigkeys`（采样）、RDB 离线分析（redis-rdb-tools）、慢查询日志
* 治理：**拆分**（大 hash 按 field hash 到多个 key）、压缩 value、异步删除 `UNLINK`、避免把大 JSON 整个塞缓存

**热 key**（访问集中在个别 key，QPS 极高）：

* 危害：单分片 CPU/带宽打满，Cluster 无法水平扩展热点
* 发现：`redis-cli --hotkeys`（LFU 下）、客户端埋点统计、代理层统计
* 治理：**本地缓存兜底**（应用内存缓存热点数据）、**key 打散多副本**（key_1~key_N 随机读）、读写分离扛读

## 第三部分：Kafka（消息队列）

### Q25：Kafka 的核心架构与概念？

**答：**

```
Producer ──┐                    ┌── Consumer Group
           ▼                    ▼
      ┌───────── Broker 集群 ─────────┐
      │  Topic: order-events           │
      │   P0 [Leader B1|Follower B2]   │
      │   P1 [Leader B2|Follower B3]   │
      │   P2 [Leader B3|Follower B1]   │
      │  （元数据：ZooKeeper / KRaft）  │
      └────────────────────────────────┘
```

* **Broker**：服务节点；**Topic**：消息类别；**Partition**：分区（**并行与顺序的基本单位**）
* **Replica**：分区副本（1 Leader + N Follower），**ISR**：与 Leader 保持同步的副本集合
* **Offset**：消费者在分区内的消费位移
* **Consumer Group**：同组消费者**分摊分区**（一个分区同组内只被一个消费者消费）；跨组互不影响（广播效果）
* **Coordinator**：协调消费者组 Rebalance 与位移提交

---

### Q26：Kafka 为什么吞吐量这么高？

**答：**

1. **顺序写磁盘**：消息只追加到分区日志文件尾部，磁盘顺序写接近内存速度（数百 MB/s）
2. **页缓存 Page Cache**：读写都走 OS 页缓存，尽量不碰磁盘
3. **零拷贝（sendfile）**：消费时数据从页缓存直达网卡，跳过用户态拷贝
4. **批量 + 压缩**：生产者攒批发送（`linger.ms` + `batch.size`），配合压缩
5. **分区并行**：分区分布在多 Broker，读写水平扩展
6. 稀疏索引 + 二分查找快速定位 offset

**面试要点**：能对比随机写 vs 顺序写的数量级差异（机械盘差 3~4 个数量级）。

---

### Q27：生产者如何保证消息不丢？

**答：** 生产端三步走：

1. **acks 配置**：
   * `acks=0`：发了就算，可能丢（日志类可接受）
   * `acks=1`：Leader 写入即成功，Leader 挂且未同步 → 丢
   * `acks=all（-1）`：**ISR 全部副本**写入才成功（配合 `min.insync.replicas >= 2` 防止 ISR 收缩到只剩 Leader）
2. **重试**：`retries` 设大 + `delivery.timeout.ms` 兜底，处理瞬时失败
3. **确认回调**：发送后检查回调，失败记录/重投/告警

**权衡**：acks=all 性能下降——可靠性要求低的场景（埋点日志）用 acks=1 或 0。

---

### Q28：消费者如何保证不丢、不重？

**答：**

**不丢**：**先处理后提交 offset**（手动提交）——自动提交（`enable.auto.commit=true`，默认 5s）可能在处理后、提交前崩溃，更糟的是**处理后提交前**重复，且"先提交后处理"会丢消息。

```
正确姿势：拉取消息 → 业务处理（含落库）→ 手动 commitSync/commitAsync
```

**重复消费不可避免**（处理成功但提交失败 → 重启再消费一次）→ **消费端幂等**：

* 数据库唯一键约束（业务 ID 唯一索引）
* Redis 记录已处理消息 ID（setnx + 过期）
* 状态机（订单只允许 待支付→已支付 单向流转）

**精确一次（Exactly Once）**：Kafka 事务 + 幂等生产者（`enable.idempotence=true`，PID+序列号去重）+ `read_process_write` 事务，仅覆盖 **Kafka 内部** 的读处理写闭环；对接外部系统仍要业务幂等。

---

### Q29：如何保证消息顺序？

**答：** Kafka 只保证**单分区内有序**。

* **全局有序**：Topic 只设 1 个分区（牺牲并行度，很少用）
* **局部有序（常用）**：**同一业务 key（如同一个订单号）发到同一分区**
  * 生产端：指定 `key`，按 key hash 路由
  * 消费端：单分区内单线程处理，或按 key 再哈希到线程池（保序线程模型）
* 坑：`max.in.flight.requests > 1` + 重试可能乱序 → 开启**幂等生产者**后 broker 会按序列号保序

---

### Q30：Rebalance 是什么？有什么危害？怎么减少？

**答：**

**触发条件**：消费者组成员变化（扩容/宕机/主动退出）、订阅 Topic 数变化、分区数变化。

**危害**：Rebalance 期间**整组消费者停止消费**（Stop The World），可能持续秒到分钟级，造成积压。

**减少触发**：

1. `session.timeout.ms`（默认 45s）与 `heartbeat.interval.ms`（1/3）合理设置，避免误判死亡
2. `max.poll.interval.ms` 调大（处理慢的消费者没赶上下次 poll 被踢出）
3. 消费逻辑异步化/批量提速，避免单次 poll 处理过久
4. 静态成员资格 `group.instance.id`（滚动重启不触发 Rebalance）
5. CooperativeStickyAssignor 增量再平衡（只迁移必要分区）

### Q31：消息积压怎么处理？

**答：** 先定位原因（消费慢/消费挂了/流量突增/bug 死循环），再对症：

**紧急扩容（经典方案）**：

```
1. 临时新建一个 topic，分区数 = 原 topic × N 倍
2. 写一个"搬运"消费者：不处理业务，只把消息转发到新 topic（快速分发）
3. 部署 N 倍消费者消费新 topic
4. 恢复后回归原架构
```

**消费提速**：批量拉取处理、业务异步化、优化慢逻辑（DB 批量写、去掉不必要的 RPC）、跳过可丢弃消息（重置 offset，需业务确认）。

**长期治理**：容量规划 + 监控告警（lag 阈值）、消费幂等保证可重试、上游限流。

### Q32：Kafka、RocketMQ、RabbitMQ 怎么选型？

**答：**

| 维度 | Kafka | RocketMQ | RabbitMQ |
| --- | --- | --- | --- |
| 吞吐 | **百万级/s，最高** | 十万级 | 万级 |
| 延迟 | ms 级（攒批） | ms 级 | **μs~ms 级，最低** |
| 顺序消息 | 分区内有序 | 队列有序，支持更友好 | 弱 |
| 事务消息 | 事务（Kafka 内部闭环） | **支持事务消息+回查** | 不支持 |
| 延迟消息 | 不支持（要自建） | **支持固定等级延迟** | 插件支持 |
| 重试/死信 | 需自建 | **原生死信队列、重试队列** | 原生支持 |
| 生态定位 | 大数据管道、日志流、事件流 | 电商交易类业务 | 传统企业、复杂路由 |

**口诀**：**日志大数据用 Kafka，交易业务用 RocketMQ，低吞吐复杂路由用 RabbitMQ**。

## 第四部分：高并发系统设计

### Q33：高并发的核心方法论是什么？

**答：** 记住三板斧 + 一个前提：

1. **缓存**——减少不必要的计算与 IO（多级缓存，见 Q35）
2. **异步**——非核心链路解耦，MQ 削峰填谷（写请求先落队，消费端匀速处理）
3. **拆分**——垂直拆（按业务微服务化）、水平拆（加机器横向扩展）；数据层读写分离→分库分表
4. **前提：无状态**——应用不存会话数据，才能随意扩容、流量漂移

**演进路线**：单机 → 读写分离 → 缓存 → 集群负载均衡 → 分库分表 → 异步化 → 弹性伸缩。

---

### Q34：QPS、RT、并发数是什么关系？

**答：**

* **QPS**：每秒查询/请求数
* **RT**：响应时间（看 P95/P99，别只看平均）
* **并发数** = QPS × 平均 RT（Little's Law）
  * 例：QPS 1000，平均 RT 0.2s → 同时约有 200 个在途请求

**容量估算思路**：日活 × 人均请求次数 ÷ 峰值系数（3~5 倍均值）→ 峰值 QPS → 单机容量（压测得出）→ 机器数 = 峰值 QPS / 单机 QPS × 冗余系数。

---

### Q35：多级缓存架构怎么设计？

**答：**

```
请求 → CDN（静态资源）
     → Nginx 本地缓存（热点页面）
     → 应用本地缓存（Caffeine，进程内，纳秒级）
     → 分布式缓存（Redis，跨服务共享，亚毫秒级）
     → DB（兜底真相）
```

* **本地缓存 vs 分布式缓存**：本地最快但每实例一份（不一致窗口）、容量小、重启丢失；Redis 一致但有一次网络 RT
* **Caffeine**：W-TinyLFU 淘汰，命中率高于传统 LRU
* 一致性策略：先更 DB → 删 Redis → **广播失效消息（MQ/Redis pub-sub）让各实例清本地缓存**
* 防击穿：本地缓存天然挡住热点；配合逻辑过期避免冷启动

---

### Q36：限流的四大算法？

**答：**

| 算法 | 原理 | 优缺点 |
| --- | --- | --- |
| **固定窗口计数** | 每分钟计数器，超了拒绝 | 简单；**临界突刺**（59s+61s 各打满，2 倍流量瞬间通过） |
| **滑动窗口** | 细分小格子滚动统计 | 解决临界问题；精度受格子数限制 |
| **漏桶** | 请求进桶，匀速流出 | **绝对整流**（保护下游匀速）；无法应对突发 |
| **令牌桶** | 匀速发令牌，桶里有存量 | **允许突发**（攒的令牌一次用完），主流选择 |

**单机实现**：Guava RateLimiter（令牌桶）。
**分布式限流**：Redis + Lua 脚本（计数器/令牌桶原子操作）；成熟方案 Sentinel、网关层（Nginx limit_req、Spring Cloud Gateway）。

**多维度限流**：全局限流保系统、接口级保服务、用户级防刷、商户级公平性。

### Q37：熔断降级怎么设计？

**答：** 参考 Hystrix / Sentinel 模型：

**熔断器三状态机**：

```
关闭(Closed) ──错误率超阈值──→ 打开(Open，直接快速失败/走降级)
     ↑___________________________ 冷却期后
     ←──半开(Half-Open，放探测流量：成功→关闭，失败→继续打开)
```

* 熔断指标：慢调用比例、错误率/错误数（滑动窗口统计）
* **降级策略**：默认兜底数据（推荐列表返回热门榜）、读服务降级写服务不降、同步转异步、关闭非核心功能（评论折叠、推荐下线）
* **原则**：先保交易主链路，牺牲边缘体验；降级开关配中心化配置可一键执行

---

### Q38：负载均衡有哪些算法和层次？

**答：**

**层次**：DNS（地理级）→ CDN/LVS（四层，IP+端口，性能极高）→ Nginx/网关（七层，按 URL/Header 路由）→ 客户端负载均衡（服务发现 + Ribbon/自研）→ 数据层（读写分离、分片路由）。

**算法**：

* 轮询 / 加权轮询（机器异构按配置权重）
* 最少连接 / 加权最少连接（长连接场景更精准）
* **一致性哈希**：相同请求落同一节点（会话保持、缓存命中），节点增减只影响相邻区段
* 随机（大数下近似均匀，实现最简）

### Q39：秒杀系统怎么设计？（高频综合题）

**答：** 完整回答框架：

**1. 流量漏斗：层层削减，DB 只剩涓涓细流**

```
1000万请求 → CDN静态化/答题验证码（削掉机器人与瞬时尖峰）
          → 网关限流（令牌桶，放 50万）
          → 库存预热到 Redis，预扣减（放 10万）
          → MQ 异步下单（消费端匀速）
          → DB 扣库存（几千 TPS）
```

**2. 关键设计点**：

* **页面静态化 + 按钮置灰防重**：抢购开始前 URL 动态化（防提前脚本）
* **Redis 预扣库存**：`DECR stock`，减到负数直接返回售罄；Lua 保证原子性（查库存+扣减+记录用户一人一单）
* **一人一单**：Redis Set 记录已购 uid / DB 唯一索引兜底
* **MQ 削峰**：预扣成功即返回"抢购中，结果稍后查看"，订单落库异步化
* **DB 最终扣减**：`UPDATE stock SET num = num - 1 WHERE id=? AND num > 0`（乐观防超卖）
* **热点隔离**：秒杀服务独立部署，故障不传染主站
* **降级预案**：Redis 挂了→ 限流熔断保 DB，宁可少卖不能超卖

**3. 防超卖三道防线**：Redis 原子预扣 → MQ 幂等消费 → DB 乐观扣减 + 唯一约束。

### Q40：数据库层的高并发扩展路线？

**答：** 递进式演进（别一上来就分库分表）：

1. **SQL/索引优化**（成本最低，收益最大）
2. **读写分离**：读流量走从库，写走主库
3. **缓存挡读**：热点数据进 Redis，DB 只承担缓存 miss
4. **垂直分库**：按业务域拆（配合微服务）
5. **水平分库分表**：容量与写瓶颈的根本解（见 Q14）
6. **异构查询**：复杂搜索/多维查询走 ES，统计走数仓/ClickHouse，HTAP 走 TiDB

## 第五部分：高可用系统设计

### Q41：可用性怎么度量？各 SLA 等级意味着什么？

**答：** `可用性 = (总时间 - 不可用时间) / 总时间`，以年 downtime 计：

| SLA | 年不可用时间 | 等级 |
| --- | --- | --- |
| 99% | 3.65 天 | 基本可用 |
| 99.9%（三个9） | 8.76 小时 | 普通互联网 |
| 99.99%（四个9） | 52.6 分钟 | 主流大厂核心链路 |
| 99.999%（五个9） | 5.26 分钟 | 金融/电信级 |

**面试要点**：四个9 不等于全年只允许一次 52 分钟故障——可能是**无数次数秒级抖动**的累计；MTTR（平均恢复时间）比 MTBF 更可控——**快速发现、快速切换、快速恢复**是高可用核心。

---

### Q42：高可用的本质手段是什么？

**答：** 一句话：**冗余 + 自动故障转移 + 流量隔离 + 兜底降级**。

* **冗余**：任何单点都要有备份（应用多实例、DB 主从、Redis 哨兵、Kafka 多副本、双机房）
* **自动故障转移**：健康检查（心跳）+ 自动选主/摘除（哨兵、MHA、K8s liveness、注册中心）
* **消除单点**：清单法排查——DNS、机房、网关、服务、缓存、DB、MQ、配置中心，每一环问一句"它挂了会怎样"
* **爆炸半径控制**：隔离（线程池/集群/机房级），核心与非核心物理隔离，灰度发布限制影响面
* **降级兜底**：宁可服务降功能，不能全站不可用

### Q43：各存储组件的高可用方案汇总？

**答：**

| 组件 | 高可用方案 | 数据不丢保障 |
| --- | --- | --- |
| MySQL | 主从 + MHA/Orchestrator 自动切换；MGR 多数派 | 半同步/GTID 补 binlog |
| Redis | 哨兵自动故障转移；Cluster 分片+主从 | AOF everysec / 混合持久化 |
| Kafka | 多副本 + ISR；min.insync.replicas ≥ 2 | acks=all + 持久化刷盘 |
| 应用 | 无状态多实例 + K8s 自愈 + 多可用区 | — |
| 机房 | 同城双活 / 异地多活 | 数据同步（DTS/单元化） |

**配套**：健康检查（probe）、优雅上下线（先摘流量再停）、超时与重试（必须设，防止雪崩传染）、幂等（重试的前提）。

### Q44：异地多活怎么做？

**答：**

* **同城双活**：两机房互为主备，专线低延迟（<2ms），存储层同步复制——可扛机房级故障，RPO≈0
* **异地多活**：按业务单元（如用户维度）把流量与数据分片到多个城市机房，**单元化路由**（同一用户读写固定在自己单元），跨单元数据异步同步
* 关键挑战：数据一致性冲突（同一条数据两地同时改）、全局协调服务（GTM 全局流量管理）
* **冷备/热备**：冷备平时不接流量（切换慢、数据旧），热备实时同步（成本高）
* 实际演进：多数公司止步**两地三中心**（生产+同城灾备+异地灾备），真异地多活仅头部公司

### Q45：混沌工程是什么？高可用怎么验证？

**答：** 主动注入故障，验证系统韧性（Netflix Chaos Monkey 起源）：

* 注入类型：杀进程、断网/延迟/丢包、CPU/内存打满、依赖故障（DB/Redis/MQ 挂）、机房断电
* 流程：定义稳态假设 → 注入爆炸半径内的故障 → 观测指标 → 找出弱点 → 修复 → 复验
* **配套监控**：Metrics（Prometheus/Grafana）、Logging（ELK）、**Tracing（全链路追踪）**、告警分级
- **演练纪律**：生产演练先灰度小流量、有紧急止血开关、预案文档化

## 第六部分：综合场景设计题

### Q46：缓存 + DB 的架构怎么设计？（读多写少 vs 写多读少）

**答：**

**读多写少（99% 业务，如商品详情）**：

```
读：本地缓存 → Redis → DB（miss 回填）
写：更新 DB → 删 Redis → 广播清本地
命中率优先，TTL + 随机值，热 key 预热
```

**写多读少（如计数、Feed 流）**：

```
写：先写 Redis（内存聚合），异步批量刷 DB（或 MQ 合并写）
例：点赞数 Redis INCR，定时/阈值批量 UPDATE
要点：Redis 挂了丢计数窗口 → AOF everysec + 补偿任务
极端高并发写：分片计数（counter_0~N 汇总）
```

### Q47：分布式事务怎么选型？

**答：** 先问自己：**真的需要强一致吗？** 大多数场景最终一致足够。

| 方案 | 一致性 | 性能 | 复杂度 | 适用 |
| --- | --- | --- | --- | --- |
| 2PC/XA | 强 | 差（同步阻塞） | 低 | 传统数据库间，低并发 |
| **TCC**（Try-Confirm-Cancel） | 最终（业务补偿） | 好 | 高（每接口写三段） | 资金类核心链路 |
| **本地消息表 / 事务消息** | 最终 | 好 | 中 | 异步解耦，最常用 |
| SAGA（长事务编排） | 最终 | 好 | 中 | 跨多服务长流程 |
| 最佳努力通知 | 弱 | 好 | 低 | 对外部系统的通知 |

**本地消息表思路**（面试必会）：

```
1. 业务操作 + 写消息记录 放在同一个本地事务（原子）
2. 定时任务/后台线程扫描未发送消息 → 投递 MQ（带重试）
3. 消费方处理 + 幂等，回执更新消息状态
4. 对账任务兜底不一致
```

RocketMQ 事务消息 = 把消息表内置（half 消息 + 回查机制）。

### Q48：从 0 到百万并发，系统怎么演进？

**答：** 演进式架构（面试按阶段讲，每个阶段有触发条件）：

1. **单体 + 单 DB**（日活几千）：快速上线，别过度设计
2. **读写分离 + 缓存**（QPS 数千）：慢查询出现 → 加从库、上 Redis
3. **服务化 + 负载均衡**（日活十万）：拆微服务，按域拆库
4. **异步化 + 分库分表**（日活百万）：MQ 削峰，水平拆数据，分布式 ID
5. **多级缓存 + 弹性伸缩 + 单元化**（日活千万+）：异地多活、存算分离、数据异构（ES/数仓）

**关键表达**：每一步都是**被瓶颈逼出来的**——先压测定位瓶颈（CPU/IO/带宽/锁），再对症下药，不堆砌技术。

---

### Q49：线上系统突然变慢，怎么排查？

**答：** 自上而下、由面到点：

1. **看大盘定范围**：全站慢 or 单服务慢？流量是否突增？是否刚发版？
2. **基础设施**：CPU / 内存 / GC / 磁盘 IO / 网络（`top`、`iostat`、`sar`）
3. **应用层**：接口 RT 曲线、线程池饱和度、锁竞争（`jstack` 看线程 BLOCKED/WAITING）、连接池耗尽
4. **依赖排查**（多数问题在这）：DB 慢查询/死锁（慢日志、`SHOW PROCESSLIST`）→ Redis 大 key/慢命令/是否命中率崩 → MQ 积压 → 下游 RPC 超时
5. **全链路追踪**：按 TraceID 串起调用链，定位最慢 span
6. **止血优先**：先重启/扩容/降级/回滚恢复服务，再慢慢找根因

---

### Q50：为什么说"超时、重试、幂等"是分布式铁三角？

**答：**

* **超时必设**：不设超时 → 下游抖动时线程堆积 → 级联雪崩（一次小故障放大成全站瘫痪）
* **重试要慎**：只有**瞬时错误**才重试（超时/503），次数有限 + **指数退避 + 抖动**；非幂等接口乱重试 = 重复下单
* **幂等是前提**：有重试就必须幂等（唯一索引 / token 机制 / 状态机 / Redis setnx），幂等才能放心重试

三者组合 = 分布式系统在不可靠网络上的**容错基石**。
