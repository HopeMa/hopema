### Q3：数据处理与分析的标准流程？AI 在每步扮演什么角色？

**答：**

```
1. 问题定义      —— 人主导（AI 帮澄清、追问口径）
2. 数据获取      —— AI 写取数代码（SQL/API/爬虫）
3. 数据清洗      —— AI 生成清洗代码，人定业务规则
4. 探索性分析EDA —— AI 出 checklist + 代码，人解读业务含义
5. 特征/建模     —— AI 出特征想法和模型代码，人防泄漏
6. 分析/算法实现 —— AI 写实现，人做评估设计
7. 结论与落地    —— 人负责，AI 帮表达（报告/图表）
```

**面试要点**：越靠近**业务定义与结论**的环节，人的权重越大；越靠近**代码与重复劳动**的环节，AI 的权重越大。

### Q4：什么任务适合交给 AI？什么必须人来把关？

**答：**

**适合交给 AI**：

### Q5：给 AI 布置数据任务的 Prompt 基本结构是什么？

**答：** 五要素模板：

```
【角色】你是一名资深数据分析师
【数据背景】表结构/列名/类型/3 行样例（不是全量数据！）
【任务目标】计算近 30 天各渠道的日活与留存率
【约束】Python 3.11 + pandas 2.x；输出可执行脚本；关键步骤打印中间结果
【验证要求】先 print df.shape 和 head(3)，聚合后 print 总行数
```

**关键技巧**：

* 给 **schema + 样例**，不给全量数据（省 token、防泄漏）
* 明确**库与版本**（防止 AI 用废弃 API）
* 要求**打印中间结果**（方便你逐步验证）
* 一次只布置一个小任务，分步迭代

## 第二部分：AI 辅助数据处理（中级）

### Q6：用 AI 写 Pandas 代码的最佳实践？

**答：**

**给足信息**：df 的列名/dtype/样例 + 数据量级 + 特殊说明（重复语义、缺失含义）。

**分步执行，不要一竿子到底**：

```python
# 第 1 步：先让 AI 写加载与检查代码
print(df.shape)
print(df.dtypes)
print(df.head(3))

# 第 2 步：确认无误后再写清洗逻辑
# 第 3 步：最后写聚合分析，每步 print 结果
```

**AI 写 Pandas 的常见坑（面试必答）**：

1. 用**已废弃 API**：`df.append()`（pandas 2.x 已删除）→ 提示词里锁版本
2. **链式赋值失效**：`df[df.a>0]['b'] = 1` 不生效 → 要求用 `.loc`
3. 忽略 **NaN 语义**：`groupby` 默认丢 NaN 组 → 明确 `dropna=False` 需求
4. `inplace` 趋势被移除：要求返回新对象的写法
5. 大表逐行 `apply` 慢 → 要求优先向量化/`map`/条件掩码

### Q7：什么是 Text2SQL？它为什么会出错？

**答：** Text2SQL = 把自然语言问题 + 表结构交给 LLM，生成可执行 SQL。

**典型错误来源**：

| 错误类型 | 原因 | 例子 |
| --- | --- | --- |
| 列名幻觉 | 模型编造不存在的列 | 生成 `user_age`，实际列叫 `age` |
| 口径不清 | 业务定义未告知 | "活跃用户"是登录？下单？7 日活跃？ |
| JOIN 关系错 | 缺少外键说明 | 用户表与订单表怎么关联没讲 |
| 方言差异 | 未说明数据库类型 | MySQL 语法跑在 ClickHouse 上报错 |
| 复杂问题硬写 | 多跳问题一步到位 | 应拆成 CTE 分步计算 |

**根因**：模型不了解你的 **schema 细节与业务语义**——信息不足时它不会说"不知道"，而是猜。

---

### Q8：如何系统性提升 Text2SQL 准确率？

**答：** 六板斧：

1. **完整 Schema 注入**：表名、列名、类型、**注释、外键关系、枚举值样例**
2. **业务指标字典**：把"GMV、留存、活跃"等口径写成文档随 prompt 给出
3. **Few-shot 示例**：给 3~10 组"问题 → 正确 SQL"对（从历史查数记录沉淀）
4. **先计划后写 SQL（CoT）**：要求模型先输出"涉及哪些表、怎么 JOIN、怎么过滤"再写 SQL
5. **执行校验闭环**：EXPLAIN 预检 → 只读账号 + 强制 LIMIT → 报错回传让模型自修
6. **相似问题检索（RAG）**：历史问答向量化，新问题先召回相似例再生成

**工程化产物**：Vanna 这类工具 = schema 检索 + few-shot 沉淀 + 执行反馈闭环。

### Q9：数据清洗中 AI 能帮上什么？

**答：** 先列脏数据类型，再看 AI 角色：

| 脏数据类型 | 例子 | AI 能做什么 | 谁把关 |
| --- | --- | --- | --- |
| 缺失值 | 空单元格 | 生成填充代码（fillna/插值/标记缺失列） | **人定策略**（填 0 还是中位数？） |
| 异常值 | 年龄 200 | 生成 IQR / 3σ 检测代码 | 人定业务阈值 |
| 重复数据 | 订单重复上报 | drop_duplicates 代码 | 人定判重键 |
| 格式不一 | 日期 3 种写法 | 生成正则与解析代码 ✅ 强项 | 抽查 |
| 单位混乱 | 元/万元混用 | 识别并归一代码 | 人确认换算 |
| 类别长尾 | 城市名各种写法 | **LLM 归一化映射表** ✅ 强项（'北京/北京市/BJ'→'北京'） | 人审映射表 |

**LLM 独有优势**：对**非结构化脏值**（拼写变体、口语化类别）做语义归一，这是规则做不到的。

### Q10：用 LLM 做数据标注/文本分类可行吗？怎么做才靠谱？

**答：** 可行，且是性价比最高的用法之一：

* **适合任务**：文本分类、情感分析、打标签、实体抽取、意图识别
* **标准做法**：
  1. 少样本（few-shot）给类别定义 + 每类 2~3 个例子
  2. 要求**结构化输出**（带类别与置信度）
  3. 低置信度样本转**人工复核**（人机协同）
  4. 先用 200 条人工标注做金标准，**准确率达标再放量**
* **成本控制**：批量 API（batch 半价）、简单分类用小模型
* **反向用法**：LLM 生成**合成训练数据** → 训练小模型上线（模型蒸馏思路）

### Q11：数据量很大时，AI 的局限是什么？正确模式是什么？

**答：** 核心局限：**上下文窗口装不下全量数据，且按 token 计费**。

**错误模式**：把几十万行数据贴给 AI 让它"直接分析"。

**正确模式——"AI 写代码，不搬数据"**：

```
1. 抽样：随机抽 50~100 行 + schema 给 AI 看
2. 生成：AI 针对样例写出处理/分析代码
3. 执行：代码在你的环境对全量数据跑
4. 回填：把全量运行的"统计摘要"（不是明细）喂回给 AI 做下一步
```

大数据处理三原则：**AI 见样本，机器跑全量，人看结果**。

### Q12：ETL 场景中 AI 的正确用法是什么？

**答：** 区分**开发期**与**运行期**：

* **开发期（AI 大显身手）**：
  * 写 ETL 代码：pandas / PySpark / Flink / Airflow DAG
  * 生成数据质量校验规则（空值率、主键唯一、值域检查）
  * 写数据字典、血缘文档、单元测试
* **运行期（谨慎）**：
  * 结构化数据流水线：**不要每行调 LLM**（成本 × 延迟 × 不确定性三重打击）
  * 例外：低量高价值的**非结构化数据抽取**（合同要素、报告解读）可以在流水线里调 LLM——但要做缓存、重试、质检

**一句话**：让 AI **造管道**（写 ETL 代码），别让 AI **当水**（逐行处理数据）。

## 第三部分：AI 辅助数据分析（中级）

### Q13：探索性数据分析（EDA）如何用 AI 加速？

**答：** 标准工作流：

```
第 1 步：给 AI schema + 50 行抽样，让它输出 EDA checklist
        （行数/列数/缺失/重复/类型/异常值/分布/相关性/分组差异）
第 2 步：逐项让 AI 生成代码并执行（一次一个主题）
第 3 步：把每步输出喂回，让 AI 解读"数据有什么特征"
第 4 步：人判断哪些发现与业务问题相关，决定下钻方向
```

**分工要点**：AI 负责"发现数据长什么样"（描述），人负责"这意味什么、下一步看什么"（洞察）。

**面试加分**：说出 EDA 的三层数据检查——**结构层**（shape/dtype/重复）、**质量层**（缺失/异常/不一致）、**分布层**（偏态/离群/组间差异）。

### Q14：描述性统计怎么让 AI 做对？

**答：**

* 必看指标：均值 / 中位数 / 众数 / 标准差 / 分位数 / 偏度 / 峰度
* **关键坑：不要让 AI 心算**——直接问"这组数的平均数"它会算错（LLM 数值计算不可靠）
* **正确姿势**：让 AI 写 `df.describe()` 之类的**代码**，把执行结果给它解读
* 偏态数据看中位数和分位数比均值更稳健（收入类数据必答）

### Q15：假设检验与 A/B 测试怎么做？

**答：** 流程与 AI 分工：

```
1. 提出假设       H0：新旧版本转化率无差异
2. 选检验方法      比例→卡方/z 检验；均值→t 检验；非正态→Mann-Whitney
3. 计算统计量与 p 值 —— AI 写 scipy 代码 ✅
4. 看效应量与置信区间 —— 只报 p 值是不够的（要报提升幅度）
5. 业务结论       —— 人来下（统计显著 ≠ 业务显著）
```

**必答的坑**：

* **多重检验**：同时看很多指标会"必然显著"（需 Bonferroni 校正）
* **辛普森悖论**：分组看 A 好、汇总看 B 好——分层后再下结论
* **样本量不足**：提前算 power，避免"没差异"其实是"测不出"
* ** peeking 问题**：反复看结果一显著就停 = 假阳性暴增

---

### Q16：为什么说"相关不等于因果"？AI 在这里容易犯什么错？

**答：**

* AI 极擅长发现**相关性**（冰淇淋销量与溺水人数正相关），且常会"顺嘴"给出因果解释——这是最危险的幻觉类型
* 常见混淆来源：**混杂变量**（夏天→两者都升）、**幸存者偏差**、**反向因果**

**正确的追问姿势**：

* 相关的两个变量背后有没有第三个因素？（混杂）
* 时间顺序成立吗？
* 想确认因果：RCT 随机实验 > 准实验方法（DID 双重差分、断点回归、工具变量）

**AI 的正确用法**：让它**列出可能的混杂变量**、**设计对照组**——假设由它穷举，判断由你拍板。

### Q17：数据可视化怎么借助 AI？

**答：**

**图表选型表（让 AI 推荐，人确认）**：

| 分析意图 | 推荐图表 |
| --- | --- |
| 比较 | 柱状图、条形图 |
| 分布 | 直方图、箱线图、密度图 |

**人必须把关的坑**：截断 Y 轴夸大差异、3D 饼图误导、颜色无障碍、双轴图误导。

### Q18：Code Interpreter（代码解释器）类工具是什么？和自己在 IDE 里写有什么区别？

**答：** 工作模式：上传文件 → AI 自动生成 Python → **沙箱执行** → 拿到真实输出 → 迭代修改。

* **优点**：所见即所得的闭环（AI 看到真实执行结果，不是猜）；零环境配置；适合快速分析中小数据集
* **限制**：文件大小上限、环境依赖受限、**数据离开本地**（隐私风险）、不可复现生产级流程

**选型**：探索性/一次性分析用 Code Interpreter；可复用/生产级/敏感数据回 IDE + AI 编码助手。

### Q19：如何验证 AI 给出的分析结论？（核心题）

**答：** 五道验证关卡：

1. **重算**：关键数字让 AI 用代码算，自己抽查一两个（Excel/SQL 手算核对）
2. **追问口径**：这个数怎么算出来的？涉及哪些表哪些过滤条件？——讲不清就是有问题
3. **交叉验证**：换个方法再算一遍（pandas 算完用 SQL 验）、换模型问同一问题
4. **反例测试**：故意改坏一列数据，看 AI 的结论是否跟随变化（不变化说明它在编）
5. **常识与量级校验**：GMV 突变 10 倍？先怀疑算错再怀疑业务

**一句话原则**：**AI 的输出默认是"假设"，经过验证才升级为"结论"。**

## 第四部分：AI 辅助算法实现（中高级）

### Q20：用 AI 搭建经典机器学习流水线的标准流程？

**答：** 让 AI 生成**结构化、防泄漏**的代码：

```python
from sklearn.model_selection import train_test_split, cross_val_score
from sklearn.preprocessing import StandardScaler
from sklearn.impute import SimpleImputer
from sklearn.pipeline import Pipeline
from sklearn.ensemble import GradientBoostingClassifier

# 好的生成代码应该长这样：
# 1. 先切分，再做预处理（防止泄漏）
X_train, X_test, y_train, y_test = train_test_split(
    X, y, test_size=0.2, stratify=y, random_state=42)

# 2. 预处理与模型打包进 Pipeline
pipe = Pipeline([
    ('imputer', SimpleImputer(strategy='median')),
    ('scaler', StandardScaler()),
    ('model', GradientBoostingClassifier(random_state=42)),
])

# 3. 交叉验证评估
scores = cross_val_score(pipe, X_train, y_train, cv=5, scoring='roc_auc')
pipe.fit(X_train, y_train)
```

**给 AI 的关键约束**：锁版本（sklearn 1.x）、要求 Pipeline 写法、要求打印每步评估、要求特征重要性输出。

### Q21：特征工程怎么借助 AI？

**答：** LLM 是特征头脑风暴的最佳搭档：

* **输入**：表结构 + 业务目标（预测用户流失）+ 时间粒度
* **让 AI 输出特征清单**（经典套路）：
  * RFM 类：最近一次行为距今天数、频次、金额
  * 时间窗口聚合：近 7/30/90 天活跃次数、消费均值
  * 趋势与变化率：环比、同比、斜率
  * 交叉特征：渠道 × 品类偏好
  * 行为序列：间隔方差、连续登录天数
* **人必须过滤的三个维度**：
  1. **泄漏风险**（用了事后信息，如"流失后客服联系次数"）
  2. **线上可得性**（预测时点拿得到这个特征吗）
  3. **可解释性**（业务能接受黑箱组合特征吗）

---

### Q22：模型评估指标怎么选？

**答：**

| 任务类型 | 常用指标 | 关键点 |
| --- | --- | --- |
| 分类（平衡） | Accuracy、F1 | — |
| 分类（不平衡） | Precision / Recall / F1 / AUC | 诈骗检测：Recall 优先时说清代价 |
| 回归 | MAE / RMSE / R² | RMSE 对大误差敏感 |
| 排序推荐 | NDCG / MAP / HR@K | 业务 Top-K 场景 |
| 概率校准 | Brier / 校准曲线 | 风控定价需要概率可信 |

**必答**：类别不平衡时 accuracy 会骗人（99% 负样本，全猜负也有 99%）——要看混淆矩阵与 PR 曲线；指标要和**业务代价**对齐（漏杀 vs 误杀哪个贵）。

### Q23：AI 生成的 ML 代码最常见的 bug——数据泄漏？

**答：** 数据泄漏 = 训练时用了"预测时点拿不到的信息"，表现为离线分数虚高、上线效果崩塌。

**AI 常写出的泄漏代码（必须会识别）**：

```python
# ❌ 泄漏 1：先 fit scaler 再切分
scaler.fit(X)                 # 用了全量数据的均值方差
X_train, X_test = split(X)

# ❌ 泄漏 2：目标编码用了全量标签
df['city_mean'] = df.groupby('city')['label'].transform('mean')

# ❌ 泄漏 3：按时间排序前的随机切分（用未来预测过去）
train_test_split(time_series_data)   # 应按时间先后切
```

**预防手段**：切分永远在最前、时间序列按时间切、Pipeline + ColumnTransformer 封装、让 AI 做"泄漏 review"专项检查。

### Q24：用 AI 刷算法题（LeetCode 类）的正确工作流？

**答：**

```
第一遍：自己想 15~30 分钟，写出思路（哪怕暴力解）
卡住时：只要提示不要答案（"给个方向，别给代码"）
写完后：让 AI review——时间/空间复杂度、边界、更优解法
对拍：让 AI 生成边界测试用例（空输入/单元素/极大值），验证通过
复盘：让 AI 讲同类题型的通用套路，加入自己的题单
```

**反面教材**：直接要完整答案复制——面试手写时大脑一片空白。

**AI 最大的价值**：生成对抗性测试用例 + 讲解"这类题的通用模板"（双指针/滑动窗口/单调栈）。

### Q25：什么时候用 LLM 直接做算法组件，什么时候用传统 ML？

**答：** 决策表：

| 维度 | 用 LLM 直接做 | 用传统 ML（GBDT/深度模型） |
| --- | --- | --- |
| 数据形态 | 非结构化文本、语义任务 | 结构化表格数值特征 |
| 数据量 | 少样本也能起步 | 需要标注样本量 |
| 延迟要求 | 秒级可接受 | 毫秒级 |
| 成本 | 每次调用付费 | 一次训练多次推理，边际成本低 |
| 典型场景 | 工单分类、意图识别、信息抽取 | 流失预测、风控评分、推荐排序 |

**混合架构（生产常用）**：LLM 离线做**特征提取/数据标注** → 训练小模型在线服务；或 LLM 处理文本字段生成 embedding → 与结构化特征拼接进 GBDT。

### Q26：主流 AI 编程工具怎么选？工作流是什么？

**答：**

| 工具类型 | 代表 | 交互模式 | 适合 |
| --- | --- | --- | --- |
| 代码补全 | GitHub Copilot | 写代码时行级建议 | 提升已明确需求的编码速度 |
| AI IDE | Cursor、Windsurf | 上下文感知编辑、对话改码 | 中大型项目的日常开发 |
| 编码 Agent | Claude Code、Codex、Devin | **项目级理解 + 多文件修改 + 跑命令/测试的闭环** | 复杂任务、重构、修 bug |

**Agent 化工作流（主流姿势）**：

```
1. 描述需求（清晰、可验证——最好带测试标准）
2. Agent 探索项目 → 制定计划
3. 小步执行：改代码 → 跑测试 → 看报错 → 自我修正
4. 人 review diff → 验收合并
```

**核心变化**：人的产出从"代码"变成"**清晰的需求 + 验收标准**"。

### Q27：如何让 AI 正确理解你的项目上下文？

**答：**

* **项目指令文件**：`AGENTS.md` / `CLAUDE.md` 写清技术栈、目录结构、常用命令、编码规范、禁区——AI 进入项目即读取
* **显式引用**：对话中 @具体文件/目录，而不是让 AI 猜"你说的 service 是哪个"
* **先让它复述**：复杂任务先让 AI 说出"我的理解 + 修改计划"，确认后再动手
* **保持任务聚焦**：一个会话一个主题，避免无关历史污染上下文

**面试要点**：这就是 Agent Harness 知识体系里的"上下文工程"在开发场景的应用。

### Q28：AI 生成代码的质量门禁怎么建？

**答：** "信任但验证"四层门禁：

1. **测试先行**：让 AI 先写测试（含边界用例）再写实现（TDD 式），测试通过才算完成
2. **静态检查**：lint、类型检查（mypy）、安全扫描进 CI——机器能查的不靠人眼
3. **人工 Review 重点看机器查不出的**：架构合理性、边界条件、安全敏感逻辑、业务正确性
4. **小步提交**：小 diff 才能真正被 review；大爆炸式生成 = 没有 review

**红线**：核心业务逻辑、安全模块、对外口径——AI 可以写初稿，人必须逐行过。

---

### Q29：AI 生成代码有哪些安全风险？

**答：**

| 风险 | 例子 | 对策 |
| --- | --- | --- |
| 硬编码密钥 | 生成代码里直接写 API key | 密钥扫描 + 环境变量注入 |
| 注入漏洞 | SQL/命令拼接 | 参数化查询、ORM、SAST 扫描 |
| **依赖幻觉（slopsquatting）** | 引用不存在的包名，被抢注投毒 | 锁定依赖源、人工审核新增依赖 |
| 过时 API | 用了已废弃/有 CVE 的版本 | 版本锁定 + 依赖审计 |
| 许可证污染 | 抄了 GPL 代码进商用项目 | 源头扫描工具 |

**纪律**：任何 AI 生成的依赖与密钥相关代码，review 时升一级严格度。

### Q30：什么是 Agent 化开发？哪些任务适合？

**答：** 让编码 Agent 在**闭环**里自主工作：读代码 → 改 → 跑测试 → 读报错 → 再改，人只做需求输入和最终验收。

**适合交给 Agent 的任务**：

* 有**明确验证信号**的：修 bug（测试复现）、小功能（验收用例）、重构（测试保护）
* 样板性强的：加 CRUD 接口、写单测、迁移升级、批量格式改造

**不适合**：核心架构设计、安全关键模块、需求本身模糊的任务（垃圾进垃圾出）。

**面试表达**：vibe coding（随口说需求让 AI 生成）适合原型；**生产开发 = 需求清晰 + 测试护栏 + 人审 diff**。

### Q31：用 AI 开发一个数据系统的典型架构？

**答：** 结合存储与消息队列知识（MySQL/Redis/Kafka）：

```
数据源(DB/日志/API)
   → Kafka（接入解耦）
   → 处理层 Flink/Spark（AI 开发期生成代码：清洗/聚合/特征）
   → 存储 MySQL(结果) + Redis(热点) + ES(检索)
   → 看板/接口
AI 的三个位置：
   ① 开发期：生成全部管道代码、测试、文档
   ② 运行期(受控)：Text2SQL 问答、异常根因分析、告警摘要
   ③ 运行期(谨慎)：非结构化数据的 LLM 抽取（缓存+质检）
```

**面试要点**：能说清"AI 在开发期是生产力，在运行期是受限组件"的边界。

## 第六部分：工程化与最佳实践（高级）

### Q32：数据安全与隐私怎么管？

**答：**

* **第一原则**：敏感数据（用户 PII、生产库明细、密钥）**不上传公有云 AI 服务**
* 替代方案：
  * **脱敏/采样**：给 AI 看结构与样例，不见真实敏感值
  * **合成数据**：保持分布的假数据
  * **私有化部署**：企业内网 LLM 网关（审计 + 脱敏 + 权限）
* 制度配套：员工使用规范、DLP 防泄漏工具、prompt 审计日志
* 合规：个保法/GDPR 下"数据出境"与第三方处理的评估

### Q33：Prompt 也需要资产管理吗？

**答：** 需要——好的 Prompt 是团队资产：

* **模板库**：按任务类型沉淀（Text2SQL / EDA / 特征头脑风暴 / 报告生成），版本化管理
* **Few-shot 沉淀**：历史好问答对（问题 + 正确 SQL/代码）持续入库，反哺 RAG
* **指标口径字典**：业务指标定义集中维护，随用随注入
* 复利效应：用得越久，团队查数准确率越高、新人上手越快

### Q34：AI 使用成本怎么控制？

**答：**

* **模型分级**：简单分类/格式化用小模型，复杂推理才上旗舰模型
* **缓存**：相同问题/相同文档解析结果缓存复用（语义缓存）
* **批量 API**：离线任务走 batch 接口（约半价）
* **上下文瘦身**：schema 压缩、样例截断、只给必要表——token 是最大成本项
* **度量**：建立"单任务成本"指标（每份报告/每次查询多少钱），纳入工具选型

### Q35：如何度量 AI 工具的实际效果（ROI）？

**答：** 三层指标：

1. **效率**：任务交付耗时对比（用 AI 前后）、代码产出量、查数自助率（业务自己问 vs 排队找分析师）
2. **质量**：AI 生成代码的 bug 率、测试覆盖率、Text2SQL 准确率（对金标准集）、返工率
3. **体验**：开发者满意度、采纳率（建议被接受比例）

**落地方法**：选 2~3 个高频任务（周报、取数、单测）做 A/B 对比，用数据说话。

### Q36：团队使用 AI 的协作规范怎么定？

**答：**

* AI 生成代码**必须标注**（commit / PR 说明），review 要求与人写代码一致甚至更严
* **密钥与敏感数据永不进 prompt**（红线）
* 失败案例共享：AI 踩过的坑（幻觉列名、废弃 API）沉淀进 prompt 模板与项目指令
* 新人规则：先用 AI 学，但**必须能独立解释每一行**再合并

### Q37：端到端：用 AI 产出一份"近 30 天销售下滑归因"分析报告

**答：** 参考流程（每步都体现 AI 用法 + 人工验证）：

```
1. 定义问题与口径（人）        —— 下滑的定义？环比还是同比？和谁比？
2. 取数（AI 写 SQL）           —— 注入 schema + 指标字典，先 EXPLAIN 再执行
3. 数据体检（AI 生成校验代码）  —— 空值/重复/口径异常，人抽查
4. 多维拆解（AI 建议 + 人选）   —— 渠道/品类/地区/新老客/价格/量价拆分
5. 定位异动（AI 算贡献度）      —— 哪个维度贡献了主要降幅（人验证加总一致性）
6. 假设归因（AI 列假设清单）    —— 内因（活动结束/缺货）/外因（竞对/季节）
   —— 人判断哪些相关可信，区分相关与因果
7. 验证假设（AI 写验证查询）    —— 缺货 SKU 的销量变化、活动前后对比
8. 结论与建议（人定调）        —— AI 帮润色报告与图表
```

**面试要点**：全程能说清"哪步是 AI 干的、哪步是人把关的、怎么验证的"。

### Q38：设计一个 Text2SQL 数据问答系统

**答：** 架构：

```
用户问题
  ↓ 意图澄清（可选：口径追问"活跃的定义是?"）
  ↓ 知识组装（RAG）：
      · 相关表 schema（向量检索 + 关键词）
      · 业务指标字典
      · 相似历史问答 few-shot
  ↓ 生成：先输出查询计划 → 再生成 SQL（只读账号 + LIMIT）
  ↓ 校验执行：语法检查 → EXPLAIN → 执行
      · 失败：报错回传让模型自修（最多 2 轮）
  ↓ 结果呈现：表格 + 自动图表 + 每个数字的口径说明
  ↓ 反馈闭环：用户纠错 → 沉淀为新 few-shot（越用越准）
```

**关键设计点**：权限随用户（只能查他有权限的表）、大结果自动截断 + 明细落文件、答案附口径可溯源。

### Q39：用 AI 构建用户流失预测的全流程

**答：**

```
1. 定义标签（人）     —— "流失"= 30 天无登录？口径决定样本
2. 构造快照数据集     —— 特征只能用"预测时点之前"的数据（防泄漏红线）
3. 特征工程（AI 头脑风暴 + 人过滤）—— RFM/趋势/行为间隔/客服工单
4. 样本与切分         —— 按时间切分（不能用随机切分！）
5. 基线模型（AI 生成代码）—— LR 基线 → GBDT 主模型，Pipeline 封装
6. 评估（人对齐业务） —— AUC + Recall@Top-K（运营只能触达 N 人，Top-K 命中率才重要）
7. 解释（AI 生成 SHAP 分析）—— 哪些特征驱动流失，业务验证合理性
8. 落地               —— 每日离线评分 → 高分人群给运营 → 触达效果回收 → 反馈迭代
```

### Q41：反向题：哪些环节坚决不该依赖 AI？

**答：** 面试收官题，考察判断力：

2. **因果结论与对外口径**——相关当因果发布是事故
3. **敏感数据的处理边界**——合规红线

## 附录 A：Prompt 模板速查

**Pandas 清洗模板**：角色 + df schema/样例 + 脏数据说明 + 目标规则 + 打印中间结果要求

**Text2SQL 模板**：数据库类型 + 表结构（含注释/外键）+ 指标口径 + few-shot 例子 + "先给查询计划再写 SQL" + 只读 LIMIT

**EDA 模板**：schema + 抽样 + "先输出分析 checklist，我确认后逐项生成代码"

**特征头脑风暴模板**：业务目标 + 表结构 + 时间粒度 + "列出特征清单并标注泄漏风险与线上可得性"

**报告生成模板**：分析结论要点 + 受众 + "数字必须来自我提供的执行结果，不要自行计算"
